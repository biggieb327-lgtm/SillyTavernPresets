# Operational log

One row per failure that changed the system. Format is fixed — date, failure, root
cause, system patch, eval, next — nothing else. No narration, no diary. Newest first.
Full incident detail lives in `telegram-companion-bot/CHANGELOG.md`; this file is the
index of what the *system* learned.

## Where a long investigation goes (2026-08-21)

That rule was not holding. Nine rows had grown past 3,000 characters — the largest 7,724
— because a live investigation kept appending to the row as it went: corrections,
reversals, a hypothesis dying, the answer arriving days later. **Those appended updates
are the most valuable part of the record and none of them were deleted.** They were the
wrong shape for an index, not the wrong content, and the file had quietly become the
archive it says it is not.

Each of those nine now lives in **`incidents/YYYY-MM-DD-<slug>.md`**, verbatim, under the
six headings its cells came from. The row here is the index entry and links to it.

So, when a row would outgrow the table:

1. Write `incidents/<date>-<slug>.md` with the full record **first** — copy before you
   compress, so nothing depends on the summary being right.
2. Leave a row that answers what failed, why, what shipped, what pins it, and what is
   still open, ending the Failure cell with `→ [full record](incidents/….md)`.
3. Keep appending corrections to the **incident file**, not the row. A verdict that
   reverses later belongs in the record; the row says which way it settled.

The `oplog-rows-are-index` eval caps a row at 3,000 characters. That ceiling stops the
regression; it is not a claim that 2,900 reads as an index. Rows in the 2,000–2,900 band
were left alone deliberately — rewriting fifty accurate records to chase a rounder number
risks losing detail for a benefit nobody has asked for.

Pipes inside inline code must be escaped as `\|`, or markdown reads them as column
separators and the row renders with the wrong number of cells (three rows did, for weeks).
Beware a row containing a triple backtick: its backtick count is odd, so any tool pairing
them will run past a real separator.

## Evidence tags (adopted 2026-07-27)

**Tag each load-bearing claim in a Root-cause cell with how it was learned.** Adapted
from the `evidence_kind` enum in the Shared Session Memory Protocol
(`telegram-companion-bot/REVIEW-SESSIONMEMORY-2026-07-27.md`).

| Tag | Means | Ages by |
|---|---|---|
| `[observed]` | Seen happen — a log line, a user report, live command output | going stale |
| `[code]` | Read in the source at a cited location | the file drifting |
| `[external]` | Behavior of something we don't control — PTB, Telegram, Android, a model | the vendor changing it |
| `[decision]` | Chosen, not discovered | being revisited |
| `[hypothesis]` | Consistent with the evidence, never confirmed | never — it stays unproven until someone confirms it |

**Why:** C5 (*label a theory as a theory*) and C8 (*ask what a reading actually
measures*) are both violations that only exist in prose, and both recurred. A row
already tries to carry this informally — "mechanism genuinely unconfirmed" (2026-07-17),
"no flag was proven to drive the injection" (2026-07-27) — but only when the writer
remembered to. The tag makes the distinction structural: an untagged claim in a
root-cause cell is an unfinished one, and a `[hypothesis]` can never be silently cited
later as a `[code]` fact.

Retrofitting the 29 pre-existing rows is deliberately **not** done — the tags are for
claims written from here on, and a bulk retro-tag would be exactly the confident
reconstruction the tags exist to prevent.

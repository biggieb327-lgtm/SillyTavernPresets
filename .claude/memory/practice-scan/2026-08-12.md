## 1. [fleet memory] The grounding guard checks the quote is real, never that the claim follows from it

**Pointer:** ["Eval Engineering: A Beginner's Guide"](https://emergingai.substack.com/p/eval-engineering-a-beginners-guide)
(2026-08-04) — quote: *"response quality scored 83.9%, while faithfulness to
the tool results scored only 32.3%"*, describing a system whose output looks
clean while being unsupported by its own evidence.

**Primary source:** [Ragas `Faithfulness` metric docs](https://github.com/vibrantlabsai/ragas/blob/main/docs/concepts/metrics/available_metrics/faithfulness.md)
(fetched via `raw.githubusercontent.com`, since `docs.ragas.io` is proxy-blocked)
— quote: *"A response is considered **faithful** if all its claims can be
supported by the retrieved context."* Method: decompose the response into
individual claims, check each against the source, score
`supported claims / total claims`.

**What it would change:** `_quote_grounded()` (`bot.py:2573`) is the entire
grounding check behind the `memory_ungrounded` / `note_ungrounded` guards
(`bot.py:4768`, `bot.py:4808`) — it verifies that the model's `memory_quote` /
`user_note_quote` field is a real, verbatim substring of something the user
actually said. It never checks that the extracted `memory` / `user_note` text
is *entailed* by that quote. A quote can be 100% real and grounded while the
claim built on top of it is an exaggeration or a wrong inference, and the
current guard has no way to see that gap — it is checking evidence
authenticity, not claim faithfulness, which is exactly the distinction the
Substack post's stat names.

This repo already has the machinery to close most of the gap cheaply: the
weekly `MEMORY_AUDIT` pass (`bot.py:1112`, cheap-model pass over
`memories.txt`, proposals routed through the existing `/reviewmem` queue) and
`memory_meta.json` (written per entry, `mem_meta["source"]` at `bot.py:4819`
keeps the original grounding quote alongside the stored claim). Extending
that audit's existing prompt to also flag `text` that isn't supported by its
own stored `source` — the same contradiction/superseded/stale shape it
already proposes, one more `type` in the same JSON schema at `bot.py:1176` —
would catch this class without a new subsystem. Proposal only; no code
changed here.

## 2. [operating] `hygiene-check-weekly`'s doc-drift findings stay text the owner has to act on by hand

**Pointer:** ["Shared AI Harness: One Memory, Many Models"](https://emergingai.substack.com/p/shared-ai-harness-one-memory-many)
(2026-08-11) — quote: *"OpenAI described the same problem from another
direction in its recent harness-engineering work."*

**Primary source:** OpenAI, ["Harness engineering: leveraging Codex in an
agent-first world"](https://openai.com/index/harness-engineering/), Feb 2026
(`openai.com` is proxy-blocked in this environment — fetched the verbatim
mirror at [`raw.githubusercontent.com/celesteanders/harness`](https://github.com/celesteanders/harness/blob/main/docs/research/260211_openai_harness_engineering_codex.md),
attributed to the same author/URL) — quote: *"A recurring 'doc-gardening'
agent scans for stale or obsolete documentation that does not reflect the
real code behavior and opens fix-up pull requests."*

**What it would change:** `hygiene-check-weekly` (`.claude/operating/routines.md`)
already finds exactly this class of drift — version sync, ROADMAP/
IMPROVEMENTS_PLAN vs CHANGELOG mismatches — via `context-librarian`, but its
prompt is explicitly report-only: *"make no commits, push nothing, create no
branches, modify no Routines, and edit no files... Fix nothing."* Every
finding becomes a line in a report the owner has to read and apply by hand.
The OpenAI post's pattern is one step further: for the narrow, low-risk class
of finding this Routine already produces (a stale version number, a status
line that disagrees with the changelog), open the fix as a small diff on a
proposal branch rather than only describing it — using the same
proposal-branch pattern this repo already trusts for `claude/improvement-loop`,
`claude/character-review`, and `claude/practice-scan`, just carrying an actual
patch instead of a prose file. Not a recommendation to auto-merge anything —
the owner still reviews and applies, the same posture every other Routine
already holds. Proposal only; no Routine or hook changed here.

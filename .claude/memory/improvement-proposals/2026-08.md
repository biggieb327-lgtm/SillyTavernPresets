# Improvement proposal — 2026-08

## Pattern: session start never reports how stale the local checkout is vs `origin/main`

**Occurrence 1 (2026-08-03, `fable-to-opus.md` staleness, operational-log.md row):**
`[observed]` "Verifying the live numbers hit the exact C13 trap the repo already names:
`git merge-base origin/main main` returned nothing (exit 1) — local `main` had no common
ancestor with `origin/main`, same failure shape as the 2026-07-29 false-green eval run."

**Occurrence 2 (2026-08-07, `routines.md` drift, operational-log.md row):**
`[observed]` "`git merge-base HEAD origin/main` resolved to `dee2058`, ~150 commits
behind `origin/main`'s tip, including `5f6f4f0`/`b10672b` which independently diagnosed
and applied the identical Reddit-drop the branch was re-deriving from the live trigger."
Logged in that row's Next field: "a session's local branch can be stale against
`origin/main` by a wide margin even with a real (old) merge-base, not just the
no-merge-base case C13 already names — logged as a fresh Minor entry... since the
failure mode (redundant rework, not a false-green check) differs from C13's."

Both sessions did real work (verifying numbers, re-deriving a doc fix already on `main`)
before discovering the checkout was stale — once via a rejected push, once by manually
running `git merge-base` mid-task. `.claude/hooks/session-audit.sh` already runs at
every SessionStart and reports `branch`/`uncommitted_files`, but never checks staleness
against `origin/main` — the exact gap both occurrences fell into. This is a wider case
than C13 (no merge-base at all): a *real, old* merge-base still leaves a session working
from history `origin/main` has already superseded, and nothing at session start says so.

**Proposed patch:** `.claude/hooks/session-audit.sh` — after the existing `branch`/`dirty`
lines, add:
```bash
git fetch origin main --quiet 2>/dev/null
behind=$(git rev-list --count HEAD..origin/main 2>/dev/null || echo "")
[ -n "${behind}" ] && [ "${behind}" != "0" ] && \
  echo "[session-audit] WARNING: local HEAD is ${behind} commit(s) behind origin/main — verify before trusting local docs/state or redoing work origin/main may already have"
```
Pure git, silent when in sync, and already confirmed reachable in this environment (the
2026-07-29 operational-log row: "git fetch origin main OK via the local relay").

**Eval:** new `session-audit-reports-staleness` in `.claude/evals/run-evals.sh` — run the
hook against a fixture repo with `HEAD` N commits behind a fake `origin/main` and assert
the WARNING line names N; assert silence when `HEAD == origin/main`. Break-test by
deleting the added check, confirming RED, restoring, confirming GREEN.

## External ideas (unvetted — owner approval required)

1. **[reddit idea] SKIPPED — not the anticipated failure mode.** The Apify call to
   `trudax/reddit-scraper-lite` returned HTTP 403 with body `{"error":{"type":
   "public-actor-disabled","message":"You cannot run this public Actor. Your current
   plan does not support running public Actors."}}` — an account/plan-level rejection
   from Apify itself, not the CONNECT/tunnel 403 this Routine's fallback path was
   written for. Worth the owner checking the Apify account's plan/billing if Reddit
   access is still wanted; falling back to WebSearch-only per the Routine's own rule.
   Substack: no publication URLs configured (none named by default), so skipped too.

2. **[external idea] GLM `:thinking` models can leak raw chain-of-thought into normal
   output when `max_tokens` is left high, and lowering it stopped the leak for one
   reporter.** Source: [QwenLM/qwen-code#6007](https://github.com/QwenLM/qwen-code/issues/6007)
   — "GLM-5.2 leaks thinking text as normal output when default max_tokens is 131072,"
   fixed by lowering to 8000. Fits directly: this fleet has fought the same reasoning-leak
   class three times (2026-07-20, 2026-07-29, 2026-08-03 in CHANGELOG.md) with
   detect-and-retry guards (`_looks_like_reasoning_leak`) rather than a token-budget
   lever. **Tension to flag, not resolve here:** this repo's own `MAX_TOKENS` comment
   reads "room for a thinking model to reason AND answer" (default 4096, well below the
   issue's 131072), and the 2026-07-20 changelog entry's own follow-up note points the
   *other* direction — "check the instance's MAX_TOKENS (too low for a thinking model)"
   if the leak recurs. So this idea and the repo's existing guidance disagree on which
   way to move the dial; a careful read of both before touching `MAX_TOKENS` on any
   `:thinking` instance, not a blind lower-it patch.

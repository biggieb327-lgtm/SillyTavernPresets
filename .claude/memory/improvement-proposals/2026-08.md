# Improvement proposal — 2026-08

## Pattern: a live Routine's `update_trigger` call and its `routines.md` mirror are not
enforced to land in the same session — the file's own header rule ("any change to a
live Routine's prompt must be mirrored in this file in the same session, and vice
versa") is prose only, with no mechanical check behind it.

### Occurrences (both from operational-log.md, 2026-08-07 row; corroborated in routines.md)

1. **improvement-loop-monthly** (`trig_012bvUUnBtnaE87CbBkjyAaZ`): routines.md itself
   records "**Prompt updated 2026-08-03**, owner decision (same trigger id, via
   `update_trigger`, applied to the live trigger the same day — this file's own copy
   of that update was NOT written at the time, and only caught/backfilled 2026-08-07".
2. **character-pass-monthly** (`trig_01VXMxTLk8ZKwQ61tC3JxkCA`): same day, same
   mechanism — routines.md: "**Prompt updated 2026-08-03** (same trigger id, via
   `update_trigger` — no recreate, and NOT mirrored to this file at the time — caught
   and backfilled 2026-08-07, same drift as `improvement-loop-monthly` above, same
   session)".

Operational-log's own 2026-08-07 row confirms both sat undetected for 4 days until an
unrelated session noticed by chance ("`list_triggers` ... showed `updated_at:
2026-08-03T23:4[89]:*` ... none of which existed in this branch's stale local
`routines.md`"), and explicitly ties it to a gap **already named on 2026-07-29** and
left open: "removing hygiene check 4 leaves no automatic Routine-drift detector — the
new eval guards the file's content, not file↔live-trigger equality, which is
unreachable from CI." That gap sat open 9 days before it bit twice at once.

### Why nothing caught it
No file today checks this. `hygiene-check-weekly`'s file↔trigger check was removed
2026-07-29 because fired sessions carry no MCP tools — correctly, since a *fired*
session can never call `list_triggers`. But `update_trigger` itself can only be called
from an interactive session with claude-code-remote MCP loaded — the exact session
type that already has a Stop hook (`handoff-guard.sh`/`claim-guard.sh` parse
`transcript_path` for this purpose). Nothing in `.claude/hooks/` looks at whether
`update_trigger` was called this session.

### Proposed patch
New Stop hook `.claude/hooks/routine-sync-guard.sh` (+ `routine_sync_guard.py`,
mirroring the `.sh` wrapper / `.py` logic split already used by
`handoff-guard.sh`/`handoff_guard.py`): scan `transcript_path` for any tool_use whose
name contains `update_trigger` or `create_trigger`. If one is found, require that the
same transcript also contains an Edit/Write tool_use targeting
`.claude/operating/routines.md`; if not, block the Stop (same mechanism as
`delivery-gate.sh` blocking an unlogged bot.py change) with a message pointing at the
file's own mirror rule. Register it in `.claude/settings.json`'s `Stop` array
alongside the existing hooks.

### Eval that would prove it worked
Two synthetic-transcript unit tests for `routine_sync_guard.py` (same pattern as
`handoff_guard.py`'s own tests): (a) a transcript with an `update_trigger` tool_use and
no `routines.md` Edit/Write → asserts block; (b) the same `update_trigger` call plus a
`routines.md` Edit/Write in the same transcript → asserts pass. Break-test both
branches (confirm (a) fails RED before the check exists, confirm a bug injected into
the guard — e.g. matching on the wrong tool name — makes (b) wrongly block) before
trusting either as GREEN, per this repo's standing break-test rule.
